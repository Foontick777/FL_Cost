# Резервное копирование и восстановление (DEP-01)

> Аудит stage8, находка **DEP-01 (P0)**: у проекта не было ни одного механизма
> резервного копирования. Единственная копия данных жила в docker-томе
> `postgres_data` на той же машине, что и сама база. Отказ диска, шифровальщик,
> ошибочная команда или сбой обновления = полная необратимая потеря всей
> финансовой истории компании.

## Что создано

| Файл | Назначение |
|------|-----------|
| `deploy/backup.sh` | Ежедневный дамп PostgreSQL (`pg_dump -Fc`) с проверкой читаемости, SHA-256 и ротацией 14 дней |
| `deploy/restore.sh` | Восстановление из дампа со страховочным дампом «до» и остановкой backend |
| `db_backup` (docker-compose, профиль `backup`) | Встроенный ежедневный бэкап внутри Docker без cron на хосте |

Дамп делается в формате `-Fc` (custom): сжатие встроено, можно восстановить
одну таблицу (`pg_restore --table=transactions`) без полной базы.

## Быстрый старт (вручную)

```bash
cd /opt/fleetcost            # корень проекта, рядом docker-compose.yml
./deploy/backup.sh           # → ./backups/fleetcost_20261019_033000.dump
./deploy/restore.sh backups/fleetcost_20261019_033000.dump   # восстановление
```

## Вариант А — cron на хосте (рекомендуется)

```bash
# crontab -e
BACKUP_DIR=/var/backups/fleetcost
30 3 * * *  cd /opt/fleetcost && BACKUP_DIR=/var/backups/fleetcost ./deploy/backup.sh >> /var/log/fleetcost-backup.log 2>&1
```

Храните копии на ДРУГОЙ машине/диске — бэкап на том же диске, что и база,
не спасает от отказа диска. Минимальная схема 3-2-1: 3 копии, 2 носителя,
1 — вне сервера (например, `rclone copy /var/backups/fleetcost remote:fleetcost-bak`).

## Вариант Б — встроенный сервис Docker (без cron)

```bash
docker compose --profile backup up -d db_backup
```

Сервис раз в сутки (можно менять через `BACKUP_INTERVAL_SECONDS` в `.env`)
кладёт дамп в том `db_backups`. Восстановление из такого тома:

```bash
docker compose exec db_backup ls -lh /backups
docker cp <имя-контейнера>:/backups/fleetcost_XXXX.dump ./restore.dump
./deploy/restore.sh restore.dump
```

Ограничение варианта: том живёт на том же хосте. Офлайн-копирование тома
на внешнее хранилище остаётся на вас — поэтому вариант А предпочтителен.

## Переменные окружения

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `BACKUP_DIR` | `./backups` | Куда класть дампы |
| `RETENTION_DAYS` | `14` | Ротация: копии старше N дней удаляются |
| `BACKUP_INTERVAL_SECONDS` | `86400` | Периодичность сервиса `db_backup` |
| `BACKUP_RETENTION_DAYS` | `14` | Ротация внутри сервиса `db_backup` |

## Что НЕ входит в дамп базы

1. **`.env` с секретами** — `SECRET_KEY`, `ENCRYPTION_KEY`, `POSTGRES_PASSWORD`.
   Скопируйте `.env` в надёжное место ОТДЕЛЬНО. Важно: `ENCRYPTION_KEY` нужен,
   чтобы после восстановления читались сохранённые учётные данные e100
   (они в базе зашифрованы Fernet этим ключом). База без ключа восстановима,
   но e100-учётку придётся ввести заново.
   Правило безопасности: **не храните ключ шифрования рядом с дампом** —
   дамп + ключ вместе = полный доступ ко всему.
2. **Загруженные файлы импорта** (если появятся тома с файлами) — на stage8
   всё существенное живёт в БД, отдельные файловые тома не используются.
3. **Docker-тома логов** — не критичны.

## Учебное восстановление (обязательно раз в квартал)

Бэкап, который ни разу не восстанавливали, — это надежда, а не бэкап.
Раз в квартал на тестовой машине:

```bash
# 1. Поднять чистый стек (тестовая копия репозитория + свой .env)
docker compose up -d postgres
# 2. Восстановить последний продовый дамп
./deploy/restore.sh <свежий>.dump
# 3. Поднять backend и проверить руками
docker compose up -d backend
#    → логин работает, суммы на дашборде сходятся с продом за вчера
```

Зафиксируйте в журнале: дата, кто провёл, сколько минут заняло — это и есть
ваш реальный RTO (время восстановления), который вы обязаны знать ДО аварии.

## Куда смотреть, если что-то пошло не так

| Симптом | Причина | Действие |
|---|---|---|
| `backup.sh`: «Дамп пуст» | Контейнер postgres не поднят | `docker compose ps`, поднять стек |
| `pg_restore --list` падает | Файл обрезан/перезаписан | Не использовать этот дамп; проверить предыдущий |
| Восстановление: «database is being accessed by other users» | Не все сессии остановлены | `docker compose stop backend`, повторить |
| После restore e100-провайдер не логинится | Другой `ENCRYPTION_KEY` в `.env` | Вернуть продовый `.env`, ввести учётку e100 заново |
